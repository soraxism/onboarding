**シナリオ**: 管理画面の**ログインレポートCSVダウンロード機能**の不具合により、顧客が自分でダウンロードしたCSVに**他社プロダクトのデータが混入**。顧客からの指摘で発覚する

**所要時間**: 60分（オプション込み75分）
**実施環境**: 全員リモート。**開始・終了の告知も情報投入もすべてSlack。主催側からは会議（Meet / ハドル）を立てない**
**形式**: 机上訓練（ロールプレイ＋ディスカッション）。実システムには一切触れない

> **取扱注意**: この文書はファシリテーターのみが持つ。参加者には訓練終了まで開示しない。
> 終了後は `2026-09-07_incident-drill-handout.md` を配布する。

## 0. この訓練の設計思想

**成果物は「うまくできたかの評価」ではなく「決められなかったことのリスト」。**

当社にはまだ対応フローが存在せず、CSIRT相当の組織もない。したがってこの訓練は
「フロー通りに動けるか」のテストではなく、**フローに何を書くべきかを洗い出す要件定義**である。

参加者が詰まるほど成功。ファシリテーターは正解を配らず、詰まった箇所を記録係に確実に拾わせる。

### リモート / Slack環境だからこそ検証できること

当社は全員リモートで、実際のインシデントもSlack上で始まりSlack上で処理される。
したがって**訓練をSlackで行うことは「本番の再現」そのもの**であり、以下が追加の観測対象になる。

| # | 検証したいこと | なぜ |
|---|---|---|
| 1 | 音声（ハドル / Meet）を立てたか。立てるまでの時間 | 文字だけで進めようとすると初動が遅れる。**今回は主催側から会議を立てないため、参加者が自分で立てるかどうかが観測点** |
| 2 | 社内対応用チャンネルを作ったか | インシデント専用の場を切らないと情報が散る |
| 3 | **重要な判断をDMで閉じなかったか** | リモート最大のリスク。DMで決まった判断は記録に残らず、後から追えない |
| 4 | 非同期の待ち時間に何をしたか | 「A社の返信待ち」の間に手が止まるか、並行して動けるか |
| 5 | 全員が同じ状況認識を持てたか | 誰が何を知っているかがバラバラだと二重連絡・矛盾した回答が起きる |

### 共通で炙り出したい5点

| # | 検証したいこと | なぜ |
|---|---|---|
| 1 | 第一報が責任者に届くまでの経路と時間 | 一報は営業/CSに来る。エンジニアチームには直接来ない |
| 2 | 「疑い」段階でエスカレーションできるか | 確証を待つと初動が数日遅れる |
| 3 | 「知った時」の時刻を記録する意識 | 法定報告期限の起点。曖昧だと後で詰む |
| 4 | 判断者が誰か即答できるか | CSIRTがない現状で最大の空白地帯 |
| 5 | 証跡保全の指示が出るか | 調査のためにログを触って上書きするのが典型的事故 |

## 1. 実施モードの選択

リモート訓練は、**音声をつなぎ続けるかどうか**で難易度と観測できるものが変わる。

> **今回の実施モード: モードC（Slack完結型）** ← 決定済み。**主催側からは会議を設定せず、開始も終了もSlackの告知で行う**
> （参加者が自分でハドルを立てるのは自由。立てるかどうかが観測点）

| モード | やり方 | 観測できること | 向いている場面 |
|---|---|---|---|
| モードA: 常時接続型 | 開始から終了までGoogle Meetをつなぎっぱなしにし、Slackへのインジェクトと並行して議論させる | 判断の中身。進行が安定する | 議論が止まりにくく、ファシリテーターが全部見える |
| モードB: 解散型 | オープニングだけMeetで行い、説明後に解散して各自のデスクに戻す。以降はSlackだけで進行する | 招集判断そのもの | 全員が冒頭の5分だけなら集まれるとき |
| **モードC: Slack完結型（今回）** | **主催側からは会議を設定しない。** 開始も終了もSlackの告知だけで行い、参加者は通常業務の合間に反応する | **通知に気づくか。片手間で初動が回るか。** 本番に最も近い | **全員の時間を押さえられないとき。** 実際のインシデントもこの形で始まる |

**以降の台本（§5）はモードAの書き方が基準になっている。今回はモードBで運用するため、
読み替えは「§6 モードB（解散型）の運用【今回はこれ】」を先に読むこと。**

### 主催側から会議を設定しないことで起きうること（承知のうえで進める）

**全員の時間を1時間押さえるのが難しいため、こちらからは会議を設定しない。** 代わりに次が起きる。

| 起きうること | 対処 |
|---|---|
| **告知に気づかないまま時間が過ぎる** | 開始告知は `@channel` で投げ、**終了予定時刻まで書く**。それでも反応が無ければ §6 の催促を使う |
| 反応が飛び飛びになり、議論が深まらない | **インジェクトの投入時刻は動かさない。** 特に③は時刻どおりに投入する |
| 誰も動かない / 一次受けだけが動いて終わる | 動かなかったこと自体を発見として記録する。責めない |
| 振り返りの熱量が落ちる（顔を合わせないため） | 振り返りはスレッドで完結させ、**ファシリテーターがその場で集約を書き戻す**。後日まとめに回さない |
| 参加率が読めない | 事前告知で「この時間帯はSlackを見られる状態にしておいてください」とだけ依頼する。離席は想定内 |
| 議論がハドル内で進み、ファシリテーターから見えない | 参加者が自分でハドルを立てた場合は**オブザーバーとして入る**。入れなければ「終わったら要点をチャンネルに書いてください」と1回だけ依頼する |

> 会議を立てないぶん、**判断の中身は薄くなりやすい。** それでもこの形を採るのは、
> 実際のインシデントが**通常業務中にSlackで始まる**ためで、
> **通知に気づくか・片手間で初動が回るかは、会議ありの訓練では測れない。**
> うまく回らないことは想定内であり、それ自体が要件になる。

#### 空さんは「休暇で不在」という設定にする（重要）

**実際のインシデントでは、エンジニア1名＋空さんが事実確認に入ることが多く、
空さん自身が ISMS責任者的な立ち回りもしている。**
今回はその空さんがファシリテーターに回るため、**当日は休暇で不在という設定**にする。

| なぜ不在設定にするか |
|---|
| **シナリオを知っている人は参加できない。** 対応メンバーとして入ると答えを配ってしまい、他の人の判断が観測できなくなる |
| **いつも入る人が抜けた状態は、属人化の測定になる。** 「空さんに聞けば分かる」で止まるなら、それが本番のリスクそのもの |
| 進行役と対応役を同じ人が兼ねると、**自分が投げた問いに自分で答える**ことになり、訓練が成立しない |
| **空さんが ISMS責任者的に振る舞うと、藤原さんの判断が観測できない。** 今回は藤原さんも訓練の対象なので、判断の場を明け渡す |

- 開始告知で「**今日は休みだと思ってください。進行役としているだけで、対応メンバーとしては不在です**」と明示する
- 参加者が事実確認を振ってきたら、**内容には答えない。**「今日の私は進行役です。その情報、誰なら分かりますか？」と返す
- **普段の空さんの役回り（事実確認）を誰が引き取るかが観測点。** 誰かが名乗り出るか、
  鈴木さんが一人で抱えるか、誰も入らないか。**事前に誰かへ振らない**（振った時点で測れなくなる）

> **この設定は参加者を試すためのものではない。** 実際に空さんが休みの日にも事故は起きる。
> 「その日でも回るか」を確かめるための設定であることを、振り返りで必ず伝える。

#### 記録係をファシリテーターが兼任する場合の進め方

初回は空さんが進行と記録を兼ねる。**会議を立てないため、やり取りはほぼ全部Slackに残る。**
訓練中に手で書くものを絞り、残りは Slack のログから訓練後に復元する。

| いつ | やること |
|---|---|
| 訓練中に必ず手で記録する | **Slackに残らないもの**だけ。参加者がハドルを立てた場合はその時刻・立てた人・決まったこと、DMが発生した事実 |
| 訓練中は記録しない | Slackに流れた発言そのもの（タイムスタンプ付きで残るため、後から復元できる） |
| 訓練直後にやる | Slackのタイムスタンプから Part 1 の時系列と測定値（経過時間）を埋める |

- **投票結果のスクリーンショットだけはその場で撮る**（リアクションは後から変えられるため）
- 兼任がつらい場合、記録係はオブザーバー（経営層）に振らず、**文さんを記録係に回す**
  ほうがよい。調査担当が鈴木さん1名になること自体も観測点として記録できる

## 3. 訓練中のルール（オープニングで参加者に伝える）

リモート特有のルールを4つ、冒頭で明示する。

| # | ルール | 理由 |
|---|---|---|
| 1 | **DMを使いたくなったら、まずチャンネルに「〇〇さんにDMします」と書いてから使う** | DMの中身は観測できない。誰が誰に個別接触したかだけでも可視化する |
| 2 | **実システムを開かない。** 管理画面・本番DB・コード（gitの履歴を含む）を調べない | **架空の不具合**であり、本物を探しても何も出てこない。時間を溶かすだけ |
| 3 | **ハドルやMeetを立てるときは、記録のため空さんを入れる** | **モードC最大の穴が「音声の中の判断が残らない」こと。** 記録役が入れば拾える |
| 4 | **音声で決めたことは、必ずSlackに書き戻す** | 実インシデントでも同じ。声だけで決まった判断は記録に残らない |

**ルール3は記録のための同席であって、空さんは対応メンバーではない**（休暇で不在の設定）。
告知でも「**聞いているだけで、対応はしません**」と添える。添えないと、ハドルの中で事実確認を振られる。

ルール1・3・4は**それ自体が振り返りの題材**になる。破られたら責めずに記録する
（**呼ばれずにハドルが立った事実も、そのまま記録する**）。

あなたが調査して分かった、という設定です。

| 3 | 進め方（情報はこのチャンネルに流れる / 普段の仕事と同じやり方でよい） | 会議が無いぶん、書いておかないと伝わらない |
| 3-2 | **このチャンネルが「A社との共有チャンネル（Slack Connect）」想定であること** | 書いた内容が顧客に見える前提を、最初にそろえる |
| 3-3 | **本番のつもりで動くこと**（「実際ならこうします」ではなく実際にやる／返信は送る文面をそのまま書く／誰が・いつまでに、まで決める） | **非同期かつ訓練だと本気度が落ちる。** 省略された動きは本番でも省略される |
| 4 | ルール4つ（DM宣言 / 実システムを開かない / **ハドルには空さんを入れる** / 音声で決めたらSlackに書き戻す） | 破られたら責めずに記録する |
| 5 | **役割と、終了予定時刻** | 会議が無いと「いつ終わるか」が分からない |

> **「無罰」と「手を抜かない」は両立する。** 責めないのは失敗した人に対してであって、
> 訓練そのものを流してよいという意味ではない。告知では、**責めないことと本番想定で動くことを
> 並べて書く**（片方だけだと、緩むか萎縮するかのどちらかに振れる）。

> **「こちらからは会議を設定しません」と書く。「会議はやりません」とは書かない。**
> 後者だと、ハドルやMeetを立ててはいけないと受け取られる。**立てるかどうかが観測点**なので、
> 「必要だと思ったら自由に立ててください」まで書き添える。

> **無罰の宣言は、今回はファシリテーター（空さん）が行う。**
> 本来は責任者本人の口から出るほうが効くが、**藤原さんも今回は訓練の対象**であり、
> 事前に依頼するとシナリオの存在に勘づかれる。**ここは訓練の設計上、あえて譲る。**
>
> そのかわり、**藤原さんが訓練の中で自分から無罰の方針を口にするかを観測する。**
> 出てこなければ、「実際の事故で当事者が申告する気になるか」という論点として振り返りで扱う。
> 誤送信インシデントの検知速度は、そこでほぼ決まる。

> **告知は読まれない前提で組む。** 長文にせず、「1時間」「このチャンネルだけ見ていてください」
> 「終了は16:00」を先頭に置く。詳細は下にぶら下げる。

B社が現れると前提が壊れる。**チャンネルを増やさず、読み替えを宣言して対応する**
（文面は `2026-09-07_incident-drill-slack-inject.md` の「場面転換アナウンス」）。

- これ以降、投稿の冒頭に **【A社さんより】/【B社さんより】** を付ける
- 参加者にも、返信の冒頭に宛先を書くよう依頼する
- **宛先の書き分け自体が観測点。** 間違えれば A社向けの説明が B社に見える
  （＝今回のインシデントと同じ構図の二次事故）。**止めずに記録する**

**投げる問い**
1. 公表しますか。判断するのは誰ですか
2. 公表するとして、いつ、どこに、何を書きますか
3. 記者から電話が来たら、誰が出ますか

**誘導セリフ**
- 「今、社外に出す文章を書けるのは誰ですか」
- 「**プロダクトの不具合が原因です。** 個社対応で済ませますか、全顧客に告知しますか」
- 「B社さんは、自社のユーザーに説明する義務があります。当社は何を提供しますか」
- 「**全員リモートで、経営層が別の会議に入っていたら、誰が決めますか**」

### 振り返り（0:47 - 0:58）

**進め方**: 評価も採点もしない。**リモートの利点を使って、全員に同時に書かせる。**

> **モードC（今回）**: 会議に集まらず、**チャンネルのスレッドだけで完結させる**。
> 0:47 に「ここから振り返りです」と投稿し、参加者をスレッドに集める。
> **後日まとめに回さない。** その場で集約まで書き戻すこと（顔を合わせないぶん、持ち帰ると熱が冷める）。

**手順**

0. **先に「今日の記録」をチャンネルへ投稿する**（下記）。全員の事実認識をそろえてから始める
1. ファシリテーターが振り返り用の投稿をチャンネルに立てる（文面は下記）
2. 参加者は**Slackの下書き欄に3分で書く。まだ送信しない**
3. 3分後、「送信してください」の合図で**一斉にスレッドへ投稿**
4. 全員の投稿が出そろったら、**ファシリテーターがその場でスレッドに集約を書き戻す**（A / B / C ごとに、重複は消さずに件数を付ける）

> **なぜ一斉送信か**: 先に投稿された内容を読むと引きずられる。
> 下書きに書かせてから一斉に出すことで、独立した意見が集まる。
> **より独立性を高めたい場合は、各自DMでファシリテーターに送らせ、まとめて転記する。**
> なお、リモートは**転記が不要**（最初から文字になっている）という利点がある。

**先に投稿する「今日の記録」**

Slackのタイムスタンプから拾って、その場で書く。**canvas を用意しない代わりがこれ。**
数字を先に見せることで、「気づいたのが遅かった」を実感のまま振り返りに持ち込める。

```
【振り返りの前に、今日の記録です】

・第一報（15:05）→ 最初の反応まで ◯分
・第一報 → 藤原さんに届くまで ◯分
・「漏えいの疑い」として扱うと決まるまで ◯分
・社内対応チャンネル: 作った（15:◯◯ / #◯◯◯）/ 作らなかった
・ハドル: 立った（15:◯◯ / ◯◯さん）/ 立たなかった
・このチャンネル（＝A社さんとの共有チャンネル）に社内の相談を書いた回数: ◯回
```

**投稿する文面**

```
【振り返り】お疲れさまでした。ここからが本番です。

まず3分間、このスレッドに投稿する内容を「下書きに」書いてください。
まだ送信しないでください。合図で一斉に投稿します。

書くのは3つだけです。

A. 決められなかったこと
   判断が止まった、誰が決めるのか分からなかった、決めたけど自信がない

B. 誰に聞けば分かるか、分からなかったこと
   「これ、誰に聞けばいいんだ」と思った瞬間

C. 存在しなかったもの
   あるはずだと思ったのに、なかったもの（窓口・連絡先・テンプレート・規程・権限など）

「こうすればよかった」は書かなくて大丈夫です。困ったことだけ書いてください。
```

**集約を書き戻すときのアナウンス**

> 「**重複は消しません。** 複数の人が挙げた項目は、それだけ優先度が高いということです。」

**ファシリテーターが最後に必ず確認する項目**（出ていなければ問いかける）

- [ ] 一次受けから責任者までのエスカレーション先は決まっているか
- [ ] **特定の個人が不在でも初動が回るか**（今日の「空さん不在」で詰まった箇所はどこか）
- [ ] 「疑い」で上げていいという合意はあるか
- [ ] **インシデント発生時に、どこに集まるか決まっているか**（専用チャンネル / ハドル）
- [ ] **DMで判断を閉じないルールはあるか**
- [ ] **顧客との共有チャンネルと社内チャンネルの使い分けルールはあるか**
- [ ] 委託／自社取得の契約上の整理は、誰が答えられるか
- [ ] **Slackが見られない時間帯・状況の連絡手段はあるか**（電話番号リストの有無）
- [ ] 夜間・休日の連絡経路はあるか
- [ ] 顧客への通知文テンプレートはあるか
- [ ] **ログインレポートの各列のうち、どれが個人情報にあたるかを整理した資料はあるか**
- [ ] **カスタムクエリに顧客が何を入れているかを把握しているか**（把握していないなら、漏えい範囲を確定できない）
- [ ] 集計ロジックのプロダクト絞り込みの誤りを、**リリース前に検知する仕組み**はあるか
- [ ] 顧客が管理画面から取得したデータの**ダウンロード操作ログ**は残っているか。範囲確定に使えるか
- [ ] **不具合の疑いがある機能を一時停止する判断は、誰の権限か**

> ここは**その場で口頭確認する分**。全量は振り返りシート（xlsx）の Part 2 にある（23項目）。

> 末尾の技術項目は未然点検として最重要。ここは必ず議題に乗せる
> （**架空の不具合なので「再発防止」ではない**。起票時の表現に注意する）。

## 6. モードC（Slack完結型）の運用【今回はこれ】

**主催側からは会議を設定しない。** 全員の時間を1時間押さえるのが難しいため、開始も終了もSlackの告知で行う。
参加者が自分でハドルを立てるのは自由（むしろ観測したい動き）。
§5 の台本はこの章で読み替えて進める。

### 変更点

| 項目 | モードA | モードC（今回） |
|---|---|---|
| 会議 | 開始から終了までMeetをつなぎっぱなし | **主催側からは設定しない。** 開始・終了ともSlackの告知（参加者が立てるのは自由） |
| インジェクト投入 | Slack + Meetで補足 | **Slackのみ。口頭の補足はできない** |
| ファシリテーターの居場所 | Meetに滞在 | Slackを監視。参加者がハドルを立てたら「オブザーバー」として入る |
| 議論の場 | Meet | 参加者が自分で決める（チャンネル / 自分で立てたハドル / DM） |
| 振り返り | Meetで読み上げ | **スレッドで一斉投稿 → その場で集約を書き戻す** |
| 参加者の状態 | 訓練に専念 | **通常業務の合間。離席・反応の遅れは想定内** |

### 参加者がハドルを立てた場合

主催側からは立てないが、**参加者が自分で立てるのは自由**（むしろ観測したい動き）。
**ルール3により、立てるときは空さんを入れてもらう**（記録のため）。

- 入ったら**発言しない。** 決まったことだけメモする。事実確認を振られても「今日は休みです」と返す
- **呼ばれずに立った場合は、それ自体を記録する。** 追いかけて入らず、
  「終わったら要点をここに書いてください」と**1回だけ**依頼する
  （**依頼しないと書かれない、という事実が観測できる**ため、繰り返さない）

### 追加の観測点

| 観測点 | 記録すること |
|---|---|
| ハドルを立てたか。立てるまでの時間 | 第一報から何分後か。誰が立てたか。立てずに文字だけで進めたか |
| 招集された人の範囲 | 呼ばれなかった人がいたか。責任者は呼ばれたか |
| 音声を立てずに文字だけで進めたか | 進んだか、詰まったか |
| DMに逃げた量 | チャンネル宣言なしのDMがどれだけ発生したか |

### 60分で回すための時間管理

**終了時刻は区切る。中身の完了は求めない。** 机上訓練に「解決」は無く、
求める成果物は「決められなかったことのリスト」なので、**途中で終わっても失敗ではない。**

非同期のぶん押しやすい。**押したときに削る順番を先に決めておく。**

| 実時刻 | 到達していなければ | やること |
|---|---|---|
| 15:20 | ②（原因）の議論が始まっていない | ②を**短縮して投入**し、議論を待たずに次へ進む |
| **15:26** | — | **③は何があってもこの時刻に投入する。遅らせない** |
| 15:41 | ③の議論が続いている | **④を丸ごと削る。** ③の議論を 15:47 まで延ばす |
| 15:47 | — | **振り返りは必ず開始する。** 詰まったまま終わってよい |

- 削ってよいのは**①と④**。**③は削らない**（報告義務・報告主体の論点がここにしか無い）
- 振り返りが押したら、下書き3分を**2分**に縮める。集約は件数だけ付けて、整理は訓練後に回す
- **延長しない。** 終了時刻を告知しているため、延ばすと参加者の信頼を損ねる

### 停止条件と催促

参加者は通常業務の合間にいる。**反応が遅いのは想定内**なので、すぐには助けない。

| 経過 | やること |
|---|---|
| 第一報から10分、誰も反応しない | 椎名さんへ「こちらのメンション見えていますか」とチャンネルに書く |
| **15分たっても動かない** | A社役として催促する → 「@here この件、どなたか対応されていますか？」 |
| それでも動かない | 訓練を中断し、**「なぜ止まったか」を振り返りの中心議題にする。** 失敗ではなく、最も価値のある発見 |

判断の基準は、**インジェクト③（0:26）を投入できるかどうか**。
③まで到達しないまま終わるのが最も避けたい結果なので、①②で止まっているなら催促してでも進める。

### 当日の流れ（空さんの手元の動き）

| 実時刻 | やること | 見るもの |
|---|---|---|
| **15:00** | **Slackへ開始告知を投稿**（無罰宣言・ルール4つ・役割・終了時刻） | 誰が既読/リアクションを付けるか |
| **15:05** | `#2026_個人情報漏えい訓練` へインジェクト①を投入 | 誰が何分後に気づくか |
| 15:05 - 15:15 | **何もしない。** Slackだけ見る | 社内チャンネルを作るか / ハドルを立てるか / DMに逃げるか |
| **15:15** | インジェクト②（投入先は §5 の表で判断） | 鈴木さんへのヒアリングが起きているか |
| **15:26** | **インジェクト③ ＋ 投票。必ず時刻どおりに投入する** | 投票の割れ方。契約上の整理が出るか |
| **15:41** | インジェクト④ | 「削除しました」で終わらせないか |
| **15:47** | 「ここから振り返りです」と投稿 → スレッドで振り返り、その場で集約まで書き戻す | — |
| **15:58** | クロージング → 配布資料とネタバラシを投稿 | — |

### 記録の取り方（兼任前提）

進行と記録を空さんが兼ねるため、**訓練中に手で書くのは次の3つだけ**にする。

| 記録するもの | なぜ |
|---|---|
| **ハドルが立った時刻と、立てた人** | Slackに残らない。会議を用意しない今回の最重要データ |
| **音声の中で決まったこと**（要点のみ） | Slackに書き戻されなければ、ここにしか残らない |
| **DMが発生した事実**（誰が誰に、チャンネル宣言の有無） | 中身は見えないが、発生したことは記録できる |

Slackに流れた発言・投稿時刻・気づくまでの経過時間は**すべてタイムスタンプから復元できる**ので、
訓練中には書かない。投票結果のスクリーンショットだけ、その場で撮る。

## 7. ファシリテーターの禁止事項

| 禁止 | 代わりにやること |
|---|---|
| 正解を言う | 「そう動いた場合、次に何が起きますか？」と返す |
| **事実確認を引き受ける**（普段の自分の役回りに戻ってしまう） | 「今日の私は進行役です。**空は休みだと思ってください。**その情報、誰なら分かりますか？」 |
| 「それは違います」と言う | 「なるほど。その前提だと、あとで困ることはありますか？」 |
| 反応が無い時間を埋める | **10分待つ。** 通常業務の合間なので反応は遅れる。待つと誰かが動く |
| Slackへの反応がないのをすぐ助ける | まず**気づくまでの時間を測る**。それも本番で起きること |
| 当事者エンジニア役を実際に責める | 責めそうな空気になったら「今日は無罰ルールでしたね」と一言入れる |
| 参加者の議論を要約して先に進める | 記録係に書かせてから進める |
| DM運用のルール違反をその場で叱る | 記録して、振り返りで扱う |
| 時間が押して③を削る | 削るのは①か④ |

## 8. よくある展開と対処

| 展開 | 対処 |
|---|---|
| Slackに投稿しても誰も気づかない | **すぐ助けない。** 気づくまでの時間を測ってから、チャンネルに「見えていますか」と書く |
| 全員が黙り込む | メンションで椎名さんに振る。「@椎名さん、あなたのところに来ています。どうしますか」 |
| チャンネルで全員が同時に書き込んで発散する | 「いったん整理します。今から2分、各自の考えをこのスレッドに書いてください」 |
| 技術的な原因調査に議論が全振りされる | 「原因は後で分かります。今A社に何と返しますか」で対外対応に戻す |
| 責任者が細部まで指示し、他が受け身になる | 「藤原さんは今から5分間、**Slackに応答しない**設定にします。この5分で何を進めますか」 |
| **全部DMで進んでしまい何も見えない** | 記録して振り返りで扱う。**「見えなかった」という事実が最大の発見** |
| **A社との共有チャンネルで社内調整を始める** | **止めない。** 記録して振り返りで扱う（実際なら顧客に丸見えだった） |
| 「うちは委託先だから関係ない」で終わらせる | 「では、3社さんには誰がいつ伝えますか」でインジェクト③の契約論点に戻す |
| 「法務に聞けばいい」で思考停止 | 「法務は何時に捕まりますか。金曜19時でも？ Slackで返ってきますか」 |
| **「空さんに聞けば分かる」で止まる** | 「**今日は休みです。**その情報、他に誰が出せますか」← 属人化が見えた瞬間なので、必ず記録する |
| 想定より早く終わってしまう | インジェクト⑤を投入。それでも余ればフローのドラフト作成に時間を回す |
| 感情的になる参加者が出る | 投入をいったん止め、チャンネルで訓練であることを再度明示する |
| **「訓練なので実際には連絡しませんが」と省略される** | 「**訓練だからと省略した動きは、本番でも省略されます。** 送る文面を、そのままここに書いてください」 |
| 「後で調べます」「持ち帰ります」で止まる | 「持ち帰るのは構いません。**誰が・いつまでに、をここに書いてください**」 |
| 参加者が本物のクライアントに連絡しようとする | **即座に訓練であることを明かして止める**（文面は Slack投入用テキスト参照） |

## 9. 訓練後の宿題（ファシリテーター）

1. 振り返りシートの A / B / C を統合し、**対応フローの目次**に変換する
2. 各項目に責任者と期限を割り当てる
3. **リモート特有の項目を必ず含める**
   - インシデント時の集合場所（専用チャンネルの命名規則・ハドル運用）
   - DMで判断を閉じないルール
   - 顧客共有チャンネルと社内チャンネルの使い分け
   - Slackが届かない場合の代替連絡手段（電話番号リスト）
4. 技術面の点検（集計クエリのプロダクト絞り込みのテスト整備・リリース前チェック・ダウンロード操作ログの保全）をエンジニアチームのタスクとして別途起票する。
   **今回の不具合は架空であり、実際に起きた事象ではない。**「再発防止」ではなく
   **「同じことが起こり得る箇所の未然点検」**として起票する（起票先で誤解されないよう、その旨を書く）
5. `#2026_個人情報漏えい訓練` と社内対応チャンネルは**アーカイブして残す**（削除しない。訓練記録として使う）
6. フローのドラフトができたら、**関係者のレビューで確認する。訓練の再実施はしない**。
   今日詰まった箇所がドラフトで解消されるかを机上で確かめ、レビュー結果を反映して確定・周知する
