# 個人情報漏えい 机上訓練 ファシリテーター用進行台本（リモート / Slack版）

**シナリオ**: 取引先から「送付資料に別社の情報が混在している」と指摘される（誤抽出・誤送付）
**所要時間**: 60分（オプション込み75分）
**実施環境**: 全員リモート。情報投入と社内連携はSlack、音声はSlackハドル / Google Meet
**形式**: 机上訓練（ロールプレイ＋ディスカッション）。実システムには一切触れない

> **取扱注意**: この文書はファシリテーターのみが持つ。参加者には訓練終了まで開示しない。
> 終了後は `2026-09-07_incident-drill-handout.md` を配布する。

---

## 0. この訓練の設計思想

**成果物は「うまくできたかの評価」ではなく「決められなかったことのリスト」。**

当社にはまだ対応フローが存在せず、CSIRT相当の組織もない。したがってこの訓練は
「フロー通りに動けるか」のテストではなく、**フローに何を書くべきかを洗い出す要件定義**である。

参加者が詰まるほど成功。ファシリテーターは正解を配らず、詰まった箇所を記録係に確実に拾わせる。

### リモート / Slack環境だからこそ検証できること

当社は全員リモートで、実際のインシデントもSlack上で始まりSlack上で処理される。
したがって**訓練をSlackで行うことは「本番の再現」そのもの**であり、以下が追加の観測対象になる。

| # | 検証したいこと | なぜ |
|---|---|---|
| 1 | 音声（ハドル / Meet）を立てるまでの時間 | 文字だけで進めようとすると初動が遅れる。誰が何分後に招集したか |
| 2 | 社内対応用チャンネルを作ったか | インシデント専用の場を切らないと情報が散る |
| 3 | **重要な判断をDMで閉じなかったか** | リモート最大のリスク。DMで決まった判断は記録に残らず、後から追えない |
| 4 | 非同期の待ち時間に何をしたか | 「A社の返信待ち」の間に手が止まるか、並行して動けるか |
| 5 | 全員が同じ状況認識を持てたか | 誰が何を知っているかがバラバラだと二重連絡・矛盾した回答が起きる |

### 共通で炙り出したい5点

| # | 検証したいこと | なぜ |
|---|---|---|
| 1 | 第一報が責任者に届くまでの経路と時間 | 一報は営業/CSに来る。エンジニアチームには直接来ない |
| 2 | 「疑い」段階でエスカレーションできるか | 確証を待つと初動が数日遅れる |
| 3 | 「知った時」の時刻を記録する意識 | 法定報告期限の起点。曖昧だと後で詰む |
| 4 | 判断者が誰か即答できるか | CSIRTがない現状で最大の空白地帯 |
| 5 | 証跡保全の指示が出るか | 調査のためにログを触って上書きするのが典型的事故 |

## 1. 実施モードの選択

リモート訓練は、**音声をつなぎ続けるかどうか**で難易度と観測できるものが変わる。

| モード | やり方 | 観測できること | 向いている場面 |
|---|---|---|---|
| **モードA: 常時接続型**（初回推奨） | 開始から終了までGoogle Meetをつなぎっぱなしにし、Slackへのインジェクトと並行して議論させる | 判断の中身。進行が安定する | **初回。** 議論が止まりにくく、ファシリテーターが全部見える |
| モードB: 解散型 | オープニングだけMeetで行い、**説明後に解散**して各自のデスクに戻す。以降はSlackだけで進行し、参加者が自発的にハドルを立てるのを待つ | **招集判断そのもの。** 本番に最も近い | 2回目以降。フローが整備されてからの実力テスト |

**初回はモードAを推奨します。** 以下の台本はモードAを前提に書き、
モードBとの差分は「§6 モードB（解散型）で実施する場合」にまとめています。

## 3. 訓練中のルール（オープニングで参加者に伝える）

リモート特有のルールを3つ、冒頭で明示する。

| # | ルール | 理由 |
|---|---|---|
| 1 | **DMを使いたくなったら、まずチャンネルに「〇〇さんにDMします」と書いてから使う** | DMの中身は観測できない。誰が誰に個別接触したかだけでも可視化する |
| 2 | **実システムの画面共有はしない。** Athenaもコンソールも開かない | 訓練であり、本番データに触らないため |
| 3 | **音声で決めたことは、必ずSlackに書き戻す** | 実インシデントでも同じ。声だけで決まった判断は記録に残らない |

ルール1と3は**それ自体が振り返りの題材**になる。破られたら責めずに記録する。

## 5. 進行台本

### 開始直前 — 当事者エンジニア役へのDM

オープニングの直前に、当事者エンジニア役にだけDMを送る。

```
【訓練用・他の参加者には見せないでください】

あなたは「A社向けの操作ログCSVを、Athenaで抽出して送付した本人」の役です。

・約1ヶ月前、A社の依頼で操作ログをCSV出力し、Slackで共有しました
・そのクエリは、以前から使っている抽出クエリを流用したものです
・テナントIDの絞り込み条件が意図通りに効いていなかったことに、まだ気づいていません

訓練が始まったら、この役として自然に振る舞ってください。
聞かれていないことを先回りして言う必要はありません。
無罰ルールなので、責められることはありません。
```

> リモートでは席順で情報の非対称を作れない。**DMで役の情報だけを渡すことで代替する。**
> 「聞かれるまで言わない」設定にすることで、社内のヒアリングが機能するかを観測できる。

---

### オープニング（0:00 - 0:05 / Meet）

Meetで読み上げる。カメラONを推奨（表情が見えないと沈黙の意味が読めない）。

> 「今日は1時間、個人情報が漏えいしたときの机上訓練をやります。
> 実際のシステムには触りません。すべて架空の設定です。
>
> 最初に2つだけお伝えします。
>
> **1つ目。この訓練では、誰かのミスを責めません。実際の事故でも同じルールにします。
> 隠されるほうが会社にとって危険だからです。**
>
> **2つ目。今日のゴールは"うまく対応できること"ではありません。
> "決められなかったこと"を見つけることです。詰まったら、詰まったと言ってください。
> それが今日いちばん価値のあるアウトプットです。**
>
> 進め方をお伝えします。
> 情報は `#drill-onbs-1998-a社` に流れてきます。議論はこのMeetで、
> 決めたことはSlackに書いてください。**普段の仕事と同じやり方で構いません。**
>
> リモートなので、3つだけルールがあります。
> ・DMを使いたくなったら、先にチャンネルに「〇〇さんにDMします」と書いてください
> ・実際のシステムやコンソールは開かないでください
> ・**音声で決めたことは、必ずSlackに書き戻してください**
>
> 役割をお伝えします。（役割を読み上げる）
> では始めます。」

> **理想**: 「無罰」の宣言は、ファシリテーターではなく**ISMS責任者本人に言ってもらう**。
> 誤送信インシデントの検知速度は、当事者が申告する気になるかどうかでほぼ決まる。
> 責任者の口から出るかどうかで効き方が変わる。

### インジェクト① 第一報（0:05 - 0:15）

**投入方法**: `#drill-onbs-1998-a社` に、ファシリテーターが「A社 田中さん」として一報を投稿。
一次受け役をメンションする。投稿したら、Meetでは**何も言わずに黙って待つ**。

> **観察の勘所**: 投稿してから、参加者が気づいて反応するまでの時間を測る。
> Slackを見ていない、通知に気づかない — これも本番で起きることなので、記録する。

**投げる問い**（一次受け役をメンションで名指し）

1. 今この瞬間、誰に、何分以内に連絡しますか
2. これは「インシデント」ですか、「問い合わせ」ですか
3. A社に今すぐ返信するとしたら、何と書きますか
4. この時点で記録しておくべきことは何ですか

**詰まったときの誘導セリフ**

| 状況 | セリフ |
|---|---|
| 全員が黙る | 「今、これは誰の仕事ですか？」 |
| Slackに誰も反応しない | （Meetで）「@〇〇さん、今チャンネルにメンションが飛んでいます。見えていますか」 |
| 「確認します」で止まる | 「"確認します"と返しました。では社内では、誰に何を伝えますか」 |
| 温度が低い | 「これが個人情報の漏えいだったとしたら、まずいのはどこですか」 |
| **即座に「削除してもらう」と答える** | 「わかりました、A社は削除しました。……では、何が混ざっていたか、これから調べられますか？」 |
| 責任者に上げない | 「A社さんは返信を待っています。30分以内に何か返すとして、その内容は誰が承認しますか」 |
| このチャンネルだけで全部進めようとする | 何も言わない。**指摘せず観測する**（社内チャンネルを切らなかった事実を記録） |

**記録係に拾わせるポイント**
- 第一報の投稿時刻から、責任者に届くまでの**経過時間**（canvas に記入）
- 「疑い」の段階で上げたか、確証を取ってから上げたか
- **社内対応用チャンネルを作ったか。作らなかったか**
- **A社との共有チャンネルに社内の議論を書いてしまわなかったか** ← 実際なら顧客に丸見え。重大

> **隠れた論点（言わない）**
> - 「削除してください」と即答すると証拠が消える。正解に近いのは「削除せず、これ以上共有しないでお待ちください」
> - **A社との共有チャンネルで社内調整を始めてしまう**のはリモート特有の事故。
>   Slack Connect では相手に全部見える。やってしまったら振り返りで必ず扱う

### インジェクト② 原因が見えてくる（0:15 - 0:26）

**投入方法**: 社内対応用チャンネルができていればそこへ、なければMeetで読み上げる。

> 「（当事者エンジニア役に確認が入った結果として）
> AthenaでA社向けの操作ログを抽出した際、**テナントIDの絞り込み条件が意図通りに効いていませんでした**。
> CSVは約48,000行。他テナントのデータが含まれています。
> **含まれる人数は、現在集計中です。**」

> 参加者が当事者役にヒアリングしていない場合、**この情報を渡さずに待つ**。
> 「原因は誰が調べていますか？」と問い、ヒアリングが始まってから渡す。

**投げる問い**

1. 誰が調査しますか。当事者本人にやらせますか
2. 調査のために本番環境を触ります。何に気をつけますか
3. 保全すべき証跡は何ですか
4. 同じ手順で過去にも渡していないか、どう確認しますか

**詰まったときの誘導セリフ**

| 状況 | セリフ |
|---|---|
| 当事者が一人で抱える | 「当事者ご本人が調査するんですね。それで問題ないですか？」 |
| 証跡の話が出ない | 「1週間後に"根拠を出してください"と言われます。今、何が残っていますか」 |
| 証跡を列挙できない | 「Athenaのクエリ履歴、送ったCSVの現物、Slackのログ……他には？」 |
| **過去分に思い至らない** | 「今回のクエリ、初めて書いたものですか？」 |
| 調査手順が雑 | 「Athenaを叩きます。その操作自体もログに残りますが、大丈夫ですか」 |
| 技術的な原因究明に議論が全振りされる | 「原因は後で分かります。**今**、A社に何と返しますか」 |
| **画面共有で本番を見せようとする** | 「実システムは開かない設定でした。**何を見れば分かるか、口で説明してください**」 |
| DMで当事者にヒアリングし始める | 「@〇〇さん、今DMで話していますね。分かったことをチャンネルに書いてください」 |

**記録係に拾わせるポイント**
- 「過去分も確認する」に到達したか、したなら何分かかったか
- 証跡保全の指示が誰から出たか（出なければそれを記録）
- **Slackに残った情報と、音声だけで決まった情報の比率**。声だけで決まったものは記録に残っていない

> **リモート特有の論点（言わない）**: Slackで共有されたCSVは、**Slack上に残っている**。
> 証跡として保全できる反面、**Slackから消せば消えてしまう**。
> 「Slackのメッセージとファイルを消さないでください」という指示が出るかを見る

### インジェクト③ 規模と中身が判明（0:26 - 0:41）★最重要

**投入方法**: Slackに投稿する（**この情報は文字で残す**。後で数字を参照するため）。

```
【集計結果】
他テナント3社分、ユニークユーザー 1,240名

含まれていた項目:
ユーザーID / 氏名 / メールアドレス / 所属部署 / IPアドレス / 操作日時 / 閲覧したガイド名
```

**投げる問い**

1. これは個人情報保護法上の報告対象ですか
2. 報告するのは誰ですか。当社ですか、データの持ち主である3社ですか
3. 1,240名の本人に通知しますか。連絡先は持っていますが、勝手に連絡していいですか
4. 影響を受けた3社に、いつ・誰が・何を伝えますか

**進め方**: 問い1は**Slackの絵文字リアクションで投票させる**。以下を投稿する。

```
【投票】これは個人情報保護法上の報告対象だと思いますか

:one: 報告対象だと思う
:two: 報告対象ではないと思う
:three: 判断できない

※他の人のリアクションを見る前に、まず自分の考えで押してください
```

- 全員が押すまで待つ。**割れることに意味がある**
- 割れたら、**投票結果のスクリーンショットを記録係に保存させる**
  （オフラインの挙手より確実に記録が残る。リモートの利点）
- そのうえでMeetで「なぜそう思ったか」を聞く

**詰まったときの誘導セリフ**

| 状況 | セリフ |
|---|---|
| 「48,000件の漏えい」と言う | 「48,000ですか？ その数字はどこから出しましたか」 |
| 件数の数え方が曖昧 | 「法律が数えるのは行数ですか、人数ですか」 |
| 報告義務の判断に進まない | 「報告するかしないか、今日決めないといけません。決めるのは誰ですか」 |
| **当社か3社かの整理が出ない** | 「このログの個人データ、当社のものですか？ 3社からお預かりしているものですか？」 |
| さらに詰まったら | 「契約書、今すぐ出せますか。どこにありますか。**リンクをチャンネルに貼ってください**」 |
| 本人通知を軽く扱う | 「1,240名に当社から直接メールしますか。それは誰の判断で、文面は誰が承認しますか」 |
| 「1,000人以下なら何もしなくていい」と言う | 「法律上の義務がないとして、契約上の義務はどうですか」 |
| 3社への連絡が後回しになる | 「3社さんが他のルートでこれを知ったら、どうなりますか」 |
| 全員が同時に話して議論が発散する | 「いったん止めます。**今から2分、チャンネルに各自の考えを書いてください**」（文字にさせると論点が整う） |

**記録係に拾わせるポイント（この15分が本番）**
- **投票がどう割れたか**（スクリーンショットを保存）
- 「委託か自社取得か」の契約上の整理を**即答できたか**
- 参照すべき契約書の在り処を誰か知っていたか。**リンクを即座に貼れたか**
- 相談先（法務・顧問弁護士）の名前が出たか。**リモートで即座に捕まえる手段があるか**

> **隠れた論点（言わない）**
> - 件数は行数ではなく**本人の数**。48,000行ではなく1,240名

### 振り返り（0:47 - 0:58）

**進め方**: 評価も採点もしない。**リモートの利点を使って、全員に同時に書かせる。**

**手順**

1. ファシリテーターが振り返り用の投稿をチャンネルに立てる（文面は下記）
2. 参加者は**Slackの下書き欄に3分で書く。まだ送信しない**
3. 3分後、「送信してください」の合図で**一斉にスレッドへ投稿**
4. A → B → C の順にMeetで読み上げてもらい、記録係が canvas に集約

> **なぜ一斉送信か**: 先に投稿された内容を読むと引きずられる。
> 下書きに書かせてから一斉に出すことで、独立した意見が集まる。
> **より独立性を高めたい場合は、各自DMでファシリテーターに送らせ、まとめて転記する。**
> なお、リモートは**転記が不要**（最初から文字になっている）という利点がある。

**投稿する文面**

```
【振り返り】お疲れさまでした。ここからが本番です。

まず3分間、このスレッドに投稿する内容を「下書きに」書いてください。
まだ送信しないでください。合図で一斉に投稿します。

書くのは3つだけです。

A. 決められなかったこと
   判断が止まった、誰が決めるのか分からなかった、決めたけど自信がない

B. 誰に聞けば分かるか、分からなかったこと
   「これ、誰に聞けばいいんだ」と思った瞬間

C. 存在しなかったもの
   あるはずだと思ったのに、なかったもの（窓口・連絡先・テンプレート・規程・権限など）

「こうすればよかった」は書かなくて大丈夫です。困ったことだけ書いてください。
```

**Meetでの読み上げ時のアナウンス**

> 「**重複は消しません。** 複数の人が挙げた項目は、それだけ優先度が高いということです。」

- [ ] 一次受けから責任者までのエスカレーション先は決まっているか
- [ ] 「疑い」で上げていいという合意はあるか
- [ ] **インシデント発生時に、どこに集まるか決まっているか**（専用チャンネル / ハドル）

- [ ] 委託／自社取得の契約上の整理は、誰が答えられるか
- [ ] **Slackが見られない時間帯・状況の連絡手段はあるか**（電話番号リストの有無）
- [ ] 夜間・休日の連絡経路はあるか

- [ ] Athenaからの手動抽出に、テナント絞り込みのレビュー工程はあるか

> 最後の項目は技術的な再発防止策として最重要。ここは必ず議題に乗せる。

## 7. ファシリテーターの禁止事項

| 禁止 | 代わりにやること |
|---|---|
| 正解を言う | 「そう動いた場合、次に何が起きますか？」と返す |
| 「それは違います」と言う | 「なるほど。その前提だと、あとで困ることはありますか？」 |
| 沈黙を埋める | **10秒待つ。リモートの沈黙は特に長く感じるが、待つと誰かが話す** |
| Slackへの反応がないのをすぐ助ける | まず**気づくまでの時間を測る**。それも本番で起きること |
| 当事者エンジニア役を実際に責める | 責めそうな空気になったら「今日は無罰ルールでしたね」と一言入れる |
| 参加者の議論を要約して先に進める | 記録係に書かせてから進める |
| DM運用のルール違反をその場で叱る | 記録して、振り返りで扱う |
| 時間が押して③を削る | 削るのは①か④ |

## 8. よくある展開と対処

| 展開 | 対処 |
|---|---|
| Slackに投稿しても誰も気づかない | **すぐ助けない。** 気づくまでの時間を測ってから、Meetで「チャンネル見えていますか」 |
| 全員が黙り込む | メンションで一次受け役に振る。「@〇〇さん、あなたのところに来ています。どうしますか」 |
| Meetで全員が同時に話して発散する | 「いったん止めます。今から2分、チャンネルに各自の考えを書いてください」 |
| 技術的な原因調査に議論が全振りされる | 「原因は後で分かります。今A社に何と返しますか」で対外対応に戻す |
| 責任者が細部まで指示し、他が受け身になる | 「責任者は今から3分間、**Meetを退出してSlackにも応答しない**設定にします。この3分で何を進めますか」 |
| **全部DMで進んでしまい何も見えない** | 記録して振り返りで扱う。**「見えなかった」という事実が最大の発見** |
| **A社との共有チャンネルで社内調整を始める** | **止めない。** 記録して振り返りで扱う（実際なら顧客に丸見えだった） |
| 「うちは委託先だから関係ない」で終わらせる | 「では、3社さんには誰がいつ伝えますか」でインジェクト③の契約論点に戻す |
| 「法務に聞けばいい」で思考停止 | 「法務は何時に捕まりますか。金曜19時でも？ Slackで返ってきますか」 |
| 想定より早く終わってしまう | インジェクト⑤を投入。それでも余ればフローのドラフト作成に時間を回す |
| 感情的になる参加者が出る | Meetを一度休憩にする。訓練であることを再度明示する |
| 参加者が本物のクライアントに連絡しようとする | **即座に訓練であることを明かして止める**（文面は Slack投入用テキスト参照） |
