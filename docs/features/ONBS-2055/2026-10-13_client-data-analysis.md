# ONBS-2055 先方データ（10/2〜10/9）の分析 — 10〜11時スパイクはクローラー起因で確定

## 受領データ

- `Onboardingエラー調査用データ（2026年10月2日~10月9日）.xlsm`（先方が New Relic から集計）
  - シート1: 日別・時間帯別の件数・セッション数
  - シート2: セッション単位の明細（UA・OS・デバイス・**ASN組織**・都市・件数）
- 先方の見立て: 「10〜11時の集中エラーはユーザーではなくデータセンターによる定期自動アクセスっぽい」

## 集計結果（総件数 357件/週）

### 1. 10〜11時スパイクの正体 = GCP / Microsoft のクローラー（先方の見立てどおり）

| ASN組織 | 件数/週 | UA | 発生時間帯 |
|---|---|---|---|
| GOOGLE-CLOUD-PLATFORM | 97 | **Chrome 151 / Linux / Desktop の単一UA**（Tokyo） | **11時台のみ** |
| MICROSOFT-CORP-MSN-AS-BLOCK | 67 | Chrome 153 / Linux（62）+ Chrome 124 / Mac（5） | **11時台のみ** |

- 11時台の件数は DC=170 vs 一般=10。**スパイクのほぼ全量がこの2系統**
- 毎日 23〜30件で一定、**土日も同規模** → 定期スケジュールの自動アクセス（クローラー/ボット）
- 単一UA・Linux・データセンターIP → 実ユーザーではない

### 2. エッジログとの突き合わせ（決定的な裏取り）

同時間帯（10/7 10〜12時 JST）に**当社エッジへ到達した** airmate.jp リファラのタグリクエストを
ASN 別に集計したところ、**GCP / Microsoft の ASN が1件も存在しない**（NTTドコモビジネス・
アルテリア・KDDI・SoftBank 等の一般回線のみ）。

→ クローラーは Airメイトのページを開いて JS を実行する（＝onerror と New Relic 送信は動く）が、
**サードパーティである当社タグの取得リクエスト自体を発行していない**
（検索エンジン/AI系クローラーのレンダリング環境はサードパーティリソースの取得を
スキップ・遮断するのが一般的）。当社エッジに記録が皆無だったこととも完全に整合する。

### 3. 残りの約2割（71件/週 ≈ 10件/日）= 通常のベースラインノイズ

- SoftBank・ドコモ・BIGLOBE・KDDI・IIJ 等の一般回線で、終日に散発
- 10/8 の10〜11時だけ一般回線16件 → 大半は**単一の SoftBank セッション（計10件）の再試行**で、障害性なし
- 別枠として Akamai / Fastly / Cloudflare ASN × Safari / Mac が 122件/週（終日散発）
  → **iCloud Private Relay 経由の実ユーザー**のシグネチャ。リレー経由の一時的な取得失敗で、これも日常ノイズ
- 規模感は当社エッジで観測済みの「クライアント切断（499）≈ 24件/日」と同オーダーで整合

## 結論

1. **毎日10〜11時のスパイクは GCP / Microsoft 上のクローラーによる定期巡回で確定。**
   実ユーザーへの影響はゼロ（クローラーにガイドを表示する必要はない）
2. 当社配信側に異常・対処事項はなし（初動〜エッジ調査の結論を維持）
3. 残る失敗は一般的なネットワークノイズ＋ iCloud Private Relay のゆらぎで、正常なベースライン

## 先方への回答方針

- スパイク = データセンターからの定期自動アクセス（先方の見立てを当社エッジログでも裏付け）で、
  **当社タグの取得リクエスト自体がデータセンター側から発行されていない**ことを提示
- 推奨: New Relic の監視・アラートから **データセンター ASN（またはボット判定セッション）を除外**
  すると、実ユーザーのベースライン（約10件/日）だけを監視できるようになる
- 実ユーザー分のベースラインは正常範囲であり対処不要。増加傾向が出た場合は再調査
