# AIチャットの不審なアクセスへの対応

詳細ドキュメント:
- 調査結果と対応設計: [2026-10-13_suspicious-access-investigation.md](./2026-10-13_suspicious-access-investigation.md)

---

## 概要

Slack 通知チャンネルに AI チャットのサーバーエラーが連続投稿された。
調査の結果、**配信中のクライアント JS を解析した上での意図的なプロトコル探索（ファジング）**と判断した。

突破はされていない（スキーマ検証で全て弾かれている）が、
**認証なしの公開エンドポイントに対して WAF もレート制限も無く、送信元 IP も記録していない**
構成上の問題が明らかになったため、これに対応する。

---

## 問題点

| # | 問題 | 内容 |
| --- | --- | --- |
| 1 | WAF もレート制限も無い | `terraform/` に `wafv2` リソースが存在しない |
| 2 | Cloudflare を挟んでいない | `v2ai.onboarding-app.io` は ALB への直 CNAME |
| 3 | 送信元 IP がどこにも残らない | ALB アクセスログが無効。アプリも IP を記録していない。**特定も遮断もできない** |
| 4 | Slack 通知自体が増幅器 | 1エラー＝1 `@channel`。認証なしで誰でも鳴らせる。本物の障害が埋もれる |

加えて、**実在の chatId を使われると顧客の AI 利用枠を外部から焼ける**ことも判明した（別チケット）。
chatId は顧客サイトの JS に平文で載っており、AI 実行前に利用回数がインクリメントされるため。

---

## 対応方針

対象リポジトリ: `Onboarding-AI-API` のみ（アプリと terraform の両方）

### アプリ側

- **Slack 通知の抑制**: プロトコル不一致（`action` 欠落 / 未対応 action / `Validation error`）は通知しない。
  それ以外も「同一内容は10分に1回」「全体で60秒あたり10件」のスロットリングを通す。
  抑制件数は次の通知に付記する
- **WebSocket の流量制限**: 接続単位（60秒で30メッセージ / プロトコル不一致5回連続）に加え、
  **IP 単位（60秒で300メッセージ）**でも制限する。
  クライアントは切断後に自動再接続するため、接続単位だけでは回避できるため

### インフラ側（terraform）

- **ALB アクセスログの有効化**: 保存用 S3 バケットを新設（90日で失効）。送信元 IP が残るようになる
- **WAF の導入**: ALB に Web ACL を関連付ける
  - IP 単位のレート制限（5分間 2000 リクエスト）を **BLOCK**
  - AWS マネージドルール2種は **COUNT（計測のみ）**。
    WebSocket の Upgrade を誤検知で落とすとチャットが全面停止するため、実績を見てから BLOCK を判断する
  - WAF ログは BLOCK / COUNT のみ CloudWatch Logs へ

### 採用しなかった案

- **Origin 検証**: AI チャットは顧客サイト上で動くため `Origin` は任意の顧客ドメインになる。
  固定の許可リストを作れず成立しない

---

## 影響範囲

| リポジトリ | 変更内容 |
| --- | --- |
| `Onboarding-AI-API` | `app/`（通知スロットリング / 流量制限）、`terraform/`（ALBアクセスログ / WAF） |

**正規利用への影響は無い想定。** 上限値はいずれも正規クライアントの実態
（1チャットターン＝1メッセージ、ヘルスチェックはメッセージを送らない）から見て十分に緩く、
企業の NAT 配下で同一 IP に多数の利用者が集まるケースも考慮して設定している。

---

## 残課題（別チケット）

- 実在 chatId を使った AI 利用枠の消費への対策（`Onboarding-AI-API` と `onboarding-web` にまたがる）
- WAF マネージドルールを COUNT → BLOCK へ切り替えるかの判断（数週間の実績を見てから）
