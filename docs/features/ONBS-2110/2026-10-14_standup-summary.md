# Dify のアクセス制御まわりの対応（ONBS-2110）共有メモ

2026-10-14 実施 / 対象: `onb-dify`（本番）・`onb-dify-dev`（dev）

---

## 背景

- 「Dify に Cloudflare を経由しない IP 直叩きのアクセスがあった場合、ブロックされているか」の確認から始まった
- **結論はブロックされていた**（DROP ルールが 246,000 パケットを破棄済み）
- ただし調査の過程で、**誰も気づいていなかった問題が 7 件**見つかったため、まとめて対応した

---

## 見つかった問題

- **再起動したら防御が消える状態だった**
  - iptables のルールがメモリ上にしか無く、永続化されていなかった
  - 36 週間再起動していなかったから残っていただけ
- **Cloudflare の IP リスト自動更新が 2026-01-31 から失敗し続けていた**
  - 手順書からのコピペでバックスラッシュが 4 倍になっており、正規表現が全件スキップしていた
  - 同じ原因で Slack 通知も飛ばず、**失敗に誰も気づけない状態**
- **オリジンの SSL 証明書が失効していた**
  - 本番: 283 日超過 / dev: 254 日超過
  - Cloudflare の SSL/TLS が「フル」（証明書を検証しない）のため動いてしまっていた
  - 原因は**自動更新が仕込まれていなかった**こと。firewall は無関係だった
- **dev の証明書はドメインまで間違っていた**
  - 実際に使うのは `dev.dify-stands.com` だが、証明書は `dev-dify-stands.com`（別ドメイン）で発行されていた
- **dev の `CERTBOT_EMAIL` がプレースホルダのままだった**
  - `your_email@example.com`。Let's Encrypt の失効警告メールが誰にも届いていなかった
- **Cloudflare 共用 IP による迂回が可能だった**
  - オリジンの許可条件が「送信元が Cloudflare の IP」だけ
  - 攻撃者が自分の Cloudflare アカウントでオリジン IP を向いたゾーンを作れば到達できた
  - **BE・VPN の IP 制限も Cloudflare 側で実施しているため、迂回されるとアクセス制御ごと無効化**される
- **Cloudflare とオリジンの間が中間者攻撃に対して無防備だった**
  - 「フル」は暗号化はするが証明書を検証しないため、経路上で任意の証明書を提示すれば復号できた

---

## 対応したこと

- **iptables ルールを永続化**（`docker-user-fw.service` を新設）
  - `ipset` が空のときはルールを適用せず異常終了する安全装置つき
  - **本番・dev とも実際に再起動して復元を確認済み**
- **更新スクリプトを修正**（バックスラッシュの一括置換）
  - Slack 通知も復旧
- **証明書を再取得し、自動更新を仕込んだ**
  - 本番・dev とも 2027-01-12 まで有効
  - cron で毎日点検（本番 03:30 / dev 04:00）
  - dev のメールアドレスも実在のものに修正
- **秘密ヘッダによる迂回対策を導入**
  - Cloudflare が `X-Origin-Auth` を付与し、オリジンの nginx で検証
  - ヘッダが無ければ 403。**攻撃者の Cloudflare 経由ではヘッダが付かないため弾ける**
- **SSL/TLS モードを「フル（厳格）」へ変更**
  - オリジンの証明書が検証されるようになり、中間者攻撃の経路を塞いだ

---

## 他のエンジニアに知っておいてほしいこと

- **Cloudflare の `allow-acme-challenge` ルールを消さないこと**
  - 証明書更新のために意図的に開けた穴
  - WAF のカスタムルールが Let's Encrypt の検証を 403 で弾いていたため追加した
  - **消すと証明書が更新できなくなる**
- **Dify をアップグレードしたら、秘密ヘッダ検証を再適用すること**
  - `conf.d/default.conf.template` が上書きされ、検証の 1 行が消える
  - 抜けると迂回経路が静かに復活する
- **証明書が切れるとサイトが落ちるようになった**
  - 「フル（厳格）」では期限切れ＝ 526 エラー。以前のように黙って動き続けない
  - cron と Let's Encrypt の警告メールの 2 系統で検知する想定
- **秘密ヘッダの値は本番と dev で共有している**
  - dev 側から漏れると本番も破られる。将来的に分離を検討したい
- **`.env` を変更したら `docker compose restart` では反映されない**
  - 環境変数はコンテナ作成時に固定される
  - `docker compose up -d --force-recreate` が必要

---

## 残課題（別チケット化を想定）

- **`5003/tcp` の用途が不明** — `0.0.0.0` で LISTEN しているがローカルからも応答しない。要調査
- `8125/udp`（collectd の statsd）が全インターフェースで LISTEN。`127.0.0.1` に絞りたい
- `fail2ban` の導入検討（SSH が全世界公開）
- `TLSv1.1` の無効化（本番・dev 両方）
- DNS-01 チャレンジへの移行（HTTP 到達性への依存を断てる。ACME 例外ルールも不要になる）
- 更新失敗の検知強化（ログは誰も見ないので Slack 通知など）
- `dev-dify-stands.com`（未使用ドメイン）を保有し続けるかの判断

---

## 今回の教訓

**どれも「静かに失敗し続けていた」問題だった。**
ipset の更新・Slack 通知・証明書の更新のいずれも、壊れていること自体が検知されていなかった。

**動いているように見えても、検知の仕組みが無ければ気づけない。**
今回入れた cron と警告メールも、**定期的に動作を確認しないと同じことになる**。
